Architecture (what to draw on a whiteboard)

Browser
   |
Controller   (web pages + REST)      -> maps URLs, validates input, no business rules
   |
Service      (business logic)        -> rules, transactions, "not found" handling
   |
Repository   (Spring Data JPA)       -> queries, no SQL strings in the app code
   |
Entity / Database (MySQL or H2)

Cross-cutting: GlobalExceptionHandler (consistent JSON errors),
               ReadOnlyFilter (public demo mode), seeders (starter content).

Each layer has one job. That separation is what interviewers mean by "clean architecture" in a Spring project, and it is why the service tests do not need a database.

What this project demonstrates

  • Backend fundamentals: layered design, dependency injection through constructors, DTO-free entities kept simple on purpose.
  • Data modelling: enums stored as strings, lifecycle callbacks (@PrePersist/@PreUpdate) for timestamps, and JPQL search queries with optional filters.
  • Defensive coding: input validation, a global exception handler, parameterised queries (no SQL injection), a read-only mode that blocks every write for public visitors.
  • Testing discipline: over 50 automated tests across controllers, services and repositories.
  • DevOps basics: Spring profiles (local, cloud), environment-driven port, multi-stage Dockerfile, deployment from a Git push.
  • Product thinking: attempt-first practice flow, search and filters, a learning path, and a landing page that explains the value in ten seconds.

Two-minute project pitch (adapt it in your own words)

"DevVault is a Spring Boot application I built to prepare for interviews. It stores coding problems, explained code snippets, notes and a chapter-wise learning path in MySQL. I structured it in controller, service and repository layers, validated input with Bean Validation, and covered the logic with JUnit and Mockito tests. For the public version I added a Spring profile that swaps MySQL for an in-memory H2 database and a filter that makes the site read-only, then containerised it with a multi-stage Dockerfile and deployed it so every push to GitHub redeploys. If I kept going, I would add authentication, move to Flyway migrations and cache the search queries."
