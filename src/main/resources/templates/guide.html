Interview & Aptitude Prep Guide

1. How to Analyze a Problem Statement

Before writing any code, work through these steps in order:

  1. Read the constraints first, not the examples. The input size tells you the required time complexity. As a rule of thumb: n ≤ ~20 allows exponential solutions (brute force/backtracking); n ≤ ~105-106 usually needs O(n log n) or O(n); n ≤ ~109 or larger usually demands O(log n) or O(1), which is a strong hint that binary search or a math formula is intended.
  2. Identify the "shape" of the input and the goal - is it a single array, two arrays, a string, a tree, a graph, intervals, or a stream? Match that shape against the cheatsheet below.
  3. Trace the given example by hand before coding anything. If you can't manually produce the expected output, you don't understand the problem yet.
  4. State the brute-force approach out loud first, even if you don't code it. This proves correctness-in-principle and gives the interviewer a baseline complexity to compare your optimization against.
  5. Only then optimize, using the pattern you identified in step 2.

2. Pattern Recognition Cheatsheet

Match the signal in the problem statement to the algorithm family it usually implies:

Sorted array, need a pair/triplet matching a targetTwo Pointers

"Contiguous subarray/substring" with some running propertySliding Window

3. Making Sure You Pass the Test Cases

  • Check the constraints against your complexity. If n can be 105 and your solution is O(n2), it will fail on large hidden test cases even if it passes the small example shown to you.
  • Explicitly test edge cases: empty input, a single element, all identical elements, already sorted, reverse sorted, all negative numbers, and the maximum allowed input size.
  • Watch for integer overflow when summing or multiplying large values - use long instead of int if the problem's numbers could exceed about 2 billion.
  • Re-run your logic mentally on the provided example after coding, not just before - it's easy to introduce a bug while translating your plan into code.
  • Don't assume input is well-formed unless the problem says so - null checks and bounds checks on untrusted input are often exactly what "hidden" test cases are designed to catch.

4. Common Errors and What They Usually Mean

Error Usually means... How to fix
ArrayIndexOutOfBoundsException An off-by-one in a loop bound, or accessing i+1/i-1 without a bounds check. Check < vs <= in loop conditions; guard neighbor-index access with an explicit bounds check.
NullPointerException Usually a linked list/tree traversal that forgot to check a node for null before dereferencing it (very common with fast/slow pointers). Add the null check before .next/.left/.right access, not after.
StackOverflowError Recursion with no base case, or recursion depth proportional to input size on very large input (e.g. recursing once per array element). Verify the base case terminates correctly; convert to an iterative version with an explicit stack, or add memoization to cut the depth.
ConcurrentModificationException Modifying a List/Map/Set while iterating over it with a for-each loop. Use an Iterator's own remove(), or collect changes first and apply them after the loop.
Solution is "too slow" / times out conceptually A nested loop (O(n2)) is doing work a hash map, sort, or two-pointer pass could do in O(n) or O(n log n). Ask: "am I re-scanning data I could have remembered?" That question alone finds most O(n2) → O(n) upgrades.
Wrong answer only on edge cases An edge case wasn't considered: empty input, single element, or integer overflow from using int where long was needed. Re-run the edge-case checklist in section 3 above against your specific logic.

5. How Senior Developers Think About These Questions

Every problem in the Coding Problems section now includes a "How to Recognize This Pattern" note and a "Common Mistakes" section - written from the interviewer's side of the table, not just the solution's. When reviewing a problem, read those two sections before the solution code, and try to name the pattern yourself first. That's the actual skill being tested in both aptitude rounds and technical interviews - recognizing the shape of a problem quickly, not memorizing any one specific solution.
